## 검증

### 3D 제작 피드백 반영 — 2026-10-02

공식 앱의 최소 BillboardRenderer·MeshRenderer 씬이 `unsupported component`로 거부되는 문제를 재현했다. 수정 전 같은 기준 프로젝트에서 SpriteRenderer는 두 앱 exit 0, 나머지는 exit 1이었다. 반영 범위는 공통 로딩·표시·카메라·제작 파일 경계다. 게임 사용자의 원문 피드백·답변·프로젝트·캡처는 해당 로컬 폴더에서 관리하며 public 저장소에 포함하지 않는다.

이 변경의 새 회귀 3개와 기존 워크플로 확장을 포함한 Debug·Release CTest는 각 544/544다. 기존 서버/로컬 플레이어 검증도 통과했다. 실제 두 앱에서 Full/YAxis/None의 저장 카메라 출력은 같은 960×540 픽셀이었고 잘못된 near 값은 두 앱 exit 1로 거부했다. MCP build·smoke, 패키지/공개 CI 결과는 배포 검증 후 기록한다. 키 입력 수동 플레이·별도 PC·인증된 온라인·3D 물리와 목표 아트 품질 승인은 이 캡처의 증거가 아니다.

MCP build·smoke 19개 검사와 외부 제작 루트의 실제 에디터 GLB 임포트·조회·덮어쓰기/탈출 거부를 확인했다. 두 공식 앱에서 빌보드 `.anim`의 시작/후속 캡처가 달라 모션 진행을 확인했다. 원근 깊이 캡처에서는 뒤 메시 앞의 불투명 코어 1,659px, 앞 메시가 가리는 캐릭터 7,012px, 투명 빈 영역으로 보이는 메시 1,642px를 확인했다. 기존 아트의 부분 알파 5,826px는 블렌딩 영향이 남으며 하드 알파 픽셀 에셋 승인은 아니다. 실제 목표 에셋 검수를 대체하지 않는다.

컴파일에는 기존 경고와 Lua의 C ABI 예외 해제를 위해 /EHc를 /EHc-로 덮어쓰는 D9025 경고가 남는다. 경고 없는 빌드나 MSVC 외 플랫폼 검증 완료로 표시하지 않는다. 파일 선택창·휴지통의 실제 사용자 조작, 다양한 DPI/언어 폰트, 실제 키보드 플레이·오디오 청취·별도 PC는 아직 수동 확인 범위다. 게임 창은 같은 프로세스이며 완성된 MMORPG·온라인 클라이언트·게임 내 UI 제작 기능으로 설명하지 않는다.

패키징은 기존 파일을 지우지 않고 새 출력 폴더에서 수행한다. 버전·소스 커밋·파일별 SHA-256은 release-manifest.json에, ZIP 해시는 sidecar에 기록한다. 개인 설치 설정·상세 로그·구 문서 원본·정리한 빌드 경로는 공개 자료와 분리하여 로컬에 보관한다.

나눔스퀘어라운드의 배포 근거는 [네이버 공식 글꼴 모음](https://hangeul.naver.com/font)과 [OFL 1.1 전문](https://help.naver.com/service/30016/contents/18088?lang=ko&osType=PC)이다. 2026-10-02 확인한 Regular TTF는 1,063,276 bytes이며 SHA-256은 `52862fdf05b55ba886ca21998222d9598ef84c975e68046b9a8d8f1af09228a0`이다. 폰트 내부 데이터를 변경하지 않았다.

폰트 교체 후 Debug·Release 빌드와 CTest 각각 541/541, MCP build·smoke를 확인했다. 에디터 구현에 등장하는 한글 515종과 현대 한글 11,172자의 지원을 확인하고 실제 Release 화면 및 ZIP에서 꺼낸 에디터의 메뉴·탭·요소 추가 창을 캡처했다. 로컬 검토 패키지의 76개 파일·폰트/OFL/내장 보완 폰트 고지·ZIP 해시가 원본과 일치했다. 다양한 DPI·별도 PC·게임 프로젝트의 런타임 폰트 교체는 이 검증에 포함하지 않는다.

## 0.2.2 배포 검증

정적 충돌은 기존 벡터 저장과 선형 탐색을 사용한다. 측정 없이 캐시/공간 트리/스레드를 추가하지 않았다. 새 외부 런타임 의존성이나 내장 픽셀 제작 기능은 추가하지 않았다. 변경 책임의 이유로 순수 물리·ECS 연결·온라인 장면 로드만 분리하고 앱/게임 역참조를 막았다. 개발/게임 제작/릴리즈 스킬의 실제 명령과 범위를 함께 갱신했다. 사용자 원본 피드백·에셋·GUID를 보존하고 상세 항목별 답변과 로그/해시/프레임은 게임 프로젝트의 로컬 피드백 폴더에 둔다.

### 서버 실행 주기 회귀 수정

### D02 값 계산 경계와 로컬 오류 전달 · 2026-10-03

온라인 2D 목표에서 로컬/서버/예측이 서로 다른 이동 코드를 사용하면 벽·층·속도 결과가 달라진다. 실제 PhysicsWorld2D의 이동 루프와 ObjectSystem/PlayMode/MyGame의 모든 호출자를 추적했다. 기존 Shape2D·층/레이어·상자/원 MTV·타일 질의 계약을 `Motion2D` 값 경계로 옮기고, core만 PUBLIC 링크하는 `mye_physics2d` 타깃으로 분리했다. 성공 경로의 공통 계산은 동적 할당 없이 입력 값을 읽고 결과 값만 반환한다. 월드 어댑터가 엔티티 핸들을 불투명 ID로 변환하므로 순수 계산 헤더에 ECS·에셋·렌더를 포함하지 않는다. 새 물리 라이브러리·팩토리·중복 이동 규칙은 추가하지 않았다.

`PhysicsWorld2D::Step`은 기존 void 대신 Expected를 반환한다. 모든 본체의 계산·원점 복원·범위/공간 해시 검증이 성공한 뒤 Local/WorldTransform·lastMove/hitWall을 반영하고 트리거 diff를 발행한다. 뒤의 본체가 실패했는데 앞의 위치만 변경되는 부분 적용을 막기 위함이다. ObjectSystem이 이 오류를 반환하며 기존 MyGame 실패 처리와 PlayMode의 오류 경계를 재사용한다. 이 보장은 물리 위치/결과/트리거 이력에 대한 것이며, 앞선 Lua 실행·조작 속도 설정·입력 소비를 되돌리는 전체 틱 트랜잭션은 아니다. root LocalTransform을 명시적으로 요구하고 부모가 있는 이동체는 거부한다. 부모 월드 역변환을 조용히 잘못 적용하는 기존 가정을 유지하지 않는다.

유한한 중심·AABB 경계·양수 크기·유효 형상·층 0..7·속도·dt (0,1]·반복 1..16과 타일의 보정 결과를 공통 경계에서 검사한다. 서브스텝 수는 정수 변환 전에 상한을 적용한다. 큰 유한 변위의 길이/크기 비율이 넘쳤는데 float→int 변환부터 하던 순서를 피한다. 최종 변위/원점과 법선 투영이 표현 범위를 넘으면 오류로 반환한다. 저장된 skin·snapToGround는 기존 호환 때문에 보존하지만 아직 계산에서 사용하지 않는 데이터임을 문서에 명시했다.

공간 해시는 AABB의 float 셀 좌표를 곧바로 int32로 바꾸고 두 축의 모든 셀을 순회했다. NaN/역전 범위는 삽입/콜백 전에 거부하도록 Insert/QueryAABB도 Expected로 바꿨다. 셀 좌표는 double로 계산한 뒤 정수 범위를 검사하며 반복 인덱스는 int64로 사용한다. 한 항목/쿼리의 셀 등록은 4,096개로 제한하고 큰 영역·정수 범위 밖은 기존 항목 목록과 직접 겹침 검사한다. 큰 맵 벽을 삭제하거나 크기 제한으로 거부하지 않는다. 잘못된 항목 삽입은 ItemCount를 바꾸지 않고, 셀 크기를 바꾸면 이전 인덱스를 비운다. 큰 항목이 많을 때 최악 O(n²)인 실제 한계와 측정된 병목이 생기면 트리로 바꿀 조건을 주석/가이드에 남겼다. 성능 향상 수치를 주장하지 않는다.

유한한 큰 형상을 기존 원 계산에 넣으면 제곱 거리와 제곱 반지름이 모두 무한대가 되어 겹침을 놓치거나 NaN MTV를 반환했다. 기존 형상 회귀에 큰 입력을 추가해 **555/557**, 원-원/원-상자 두 시나리오 실패를 실제 재현했다. 상자 크기 합과 원-원 거리/반지름 합은 double 중간값, 원-상자 거리는 hypot으로 계산한다. 저장 타입·좌표 계약은 바꾸지 않는다. float로 표현할 수 없는 보정은 상위 이동 오류 경계가 거부한다. 이 경계 검사는 초대형 월드의 렌더/좌표 정밀도를 보증하지 않는다.

근거는 실제 호출 경로였다. 기존 render::Camera2D에는 경계·데드존·스냅·줌·렌더 흔들림·논리 좌표 변환이 있었지만 씬에 저장하는 2D 컴포넌트가 없었다. MyGame은 매 틱 지속 카메라의 데드존을 갱신했고, native Play는 매 렌더마다 새 카메라를 캐릭터 중심에 배치했다. headless Play는 기본 원점 카메라를 넘겼다. 따라서 같은 씬도 플레이 경로마다 추종 결과가 달랐다. PlayWindow::Render는 Blit에 잔차 0을 넘기고 MyGame은 선택한 저장 카메라 대신 앱 fallback의 잔차를 썼다. MakeViewInfo는 실제 카메라 viewport 대신 960×540을 고정 기록했고 SetZoom/SetViewportSize는 기존 위치의 경계를 다시 제한하지 않았다. 함수 정의와 소비자를 따라 이 공통 원인을 확인한 뒤 수정했다.

새 외부 카메라/물리 패키지 대신 기존 계산을 재사용했다. scene::Camera2D에 current·followTarget·offset·deadzoneHalf·zoom·pixelSnap·boundsEnabled/bounds만 반영하고, 런타임 view/initialized와 흔들림 시간은 리플렉션/씬에서 제외했다. 고유 이름은 대상의 월드 XY+offset을 사용하며 카메라 자신의 위치를 다시 더하지 않는다. 빈 이름은 자신의 월드 XY+offset이므로 캐릭터의 자식으로 추종할 수 있다. 카메라 회전·스케일·Z는 시야에 적용하지 않는다. 새 기본 마을/실내 씬에 기존 캐릭터의 자식 Game Camera를 추가했고 PNG·.meta GUID·캐릭터/오브젝트 설정은 보존했다.

UpdateGameCamera2D는 장면 진입 dt=0으로 초기 위치를 확정하고 양수 고정 틱에서 데드존/줌/흔들림을 진행한다. 초기화 전 첫 이동을 새 초기 위치로 오인해 데드존을 건너뛰지 않도록 Play 스냅샷·ObjectSystem 초기화·MyGame 장면 진입을 연결했다. 로컬 ObjectSystem은 최종 WorldTransform 뒤 호출하고, 인증 MyGame은 예측/보정/원격 표시 적용 뒤 같은 계산을 호출한다. BuildGameView는 2D/3D를 합쳐 current 하나를 선택하고 복사본만 해석한다. 렌더/조회는 카메라의 추종 상태나 흔들림 시간을 진행시키지 않는다. 저장 카메라가 없는 이전 씬은 UpdateDefaultCamera2D로 초기 중심과 고정 틱 데드존을 공유한다. 이전 3D orbit/물리/인증 이동은 유지했다.

HybridViewInfo에 선택 카메라의 subpixelResidual을 넣어 MyGame/native Play의 확대 패스가 같은 값을 사용하게 했다. 3D는 0이다. MakeViewInfo의 실제 viewport 크기·깊이 범위와 카메라의 줌/뷰 크기 변경 후 경계 재적용도 공통 계산에서 수정했다. low-level 줌 setter/생성자의 비유한 값은 기존 값/기본값으로 방어하고, 저장 Camera2D에서는 잘못된 줌/데드존/경계/이름/viewport를 Expected 오류로 거부한다. 유한한 최대 float에서도 픽셀 스냅 중 오버플로할 수 있으므로 계산 결과를 검사하고 실패 시 카메라의 view/zoom/initialized를 커밋하지 않는다. 월드/Lua 전체 틱 롤백을 구현했다고 주장하지 않는다.

Entity:set_camera_zoom·shake_camera·world_to_screen·screen_to_world는 기존 EcsBindingModule에 추가했다. 줌 0.25~8, 흔들림 0~10 unit/0~60초와 좌표의 유한성을 검사한다. 좌표 변환은 논리 중심·960×540 내부 픽셀 기준이며 흔들림/스냅을 제외한다. 삭제 Entity/누락 Camera2D/잘못된 설정은 Lua 오류다. Expected의 오류 문자열을 Lua 스택으로 옮긴 뒤 C++ 객체를 파기하고 lua_error를 호출해 오류 경계에서 C++ 수명을 보존했다. 선택 모듈 mye.camera의 미연결 서비스와 새 Entity 경로를 가이드에서 구분했다. 인증 클라이언트의 Lua 격리는 유지했으며 서버 게임 이벤트로 흔들림을 복제하는 기능은 구현하지 않았다.

native Play/MyGame은 PreUpdate에서 휠 delta를 누적하고 FixedUpdate의 exchange로 한 번 소비한다. Camera2D가 없으면 별도 줌 카메라를 자동 생성하지 않는다. MyGame의 기존 입력 재생은 선택 cameraZoomSteps -16~16을 검증해 같은 경로로 전달한다. 이는 각 틱의 시각 입력이며 서버 이동 패킷/프로토콜에는 넣지 않았다. 실제 하드웨어 휠/키·패드/포커스의 사용감과 액션 재매핑은 다음 D07에서 검증해야 한다.

## 2026-10-03 · 프로젝트 입력 설정과 공통 고정 틱 소비

결론: 파일 메뉴의 입력 설정에서 기본 조작을 편집·별도 저장하고 Play/MyGame 로컬·인증 클라이언트가 같은 계산을 소비하도록 연결했다. D07의 첫 단위이며 전체 D07·MMORPG 제작/출시는 아직 완료되지 않았다. 이전 기준선은 main 816b196이다. 다음 단위는 사용자 액션 Lua/작성 UI, 원시 패드 축/데드존, 직접 키·휠·패드와 포커스·좁은 화면/고해상도 검수다. 이미 배포한 0.3.0과 사용자 프로젝트/에셋은 변경하지 않았다.

요구와 근거: 2D MMORPG 제작을 우선하고 일을 작게 나눠 진행하라는 사용자 지시와 22번 작업 목록의 D07을 적용했다. 기존 myengine-development와 imgui-ui-ux-engineering를 읽고 적용했다. 공식 입력 설정/액션·원형 데드존·프레임/물리 틱 구분을 확인한 비교 자료와 URL은 ignored build/2d-foundation/d07-benchmark.md에 보관했다. 외부 코드를 복사하거나 새 라이브러리·스킬 패키지·에이전트를 추가하지 않았다. 기존 라이선스 고지는 보존했다.

변경 전 호출 경로: MyGame PreUpdate는 E·Space/패드 A·휠/오른쪽 드래그를 별도 누적하고 FixedUpdate는 WASD/방향키+왼쪽 스틱·Q/R+오른쪽 스틱을 직접 읽었다. EditorModule은 별도의 E·Space·휠/드래그 누적과 WASD/Q/R 계산을 사용했으며 Play 창은 오른쪽 버튼/키만 처리하고 휠·패드 폴링·다른 마우스 버튼이 빠져 있었다. InputState의 이전/현재 스냅샷 비교는 같은 입력 프레임 안의 짧은 tap을 잃는 기존 정책이었다. 관련 정의와 앱/바인딩/테스트 호출자를 확인한 뒤 이 공통 경계에서 수정했다.

구조와 선택: core InputMap/InputActions는 이름·세기·바인딩·검증·프레임 캡처/틱 소비만 담당하고 runtime GameInputBuffer는 12개 기본 게임 조작을 조합한다. 저장 키는 runtime 한곳에서 기본값·설명·소비자가 공유한다. 순환 의존성·단일 구현용 인터페이스/팩토리를 추가하지 않았다. 구성 때만 상태 벡터를 할당하며 틱 소비는 기존 저장 공간을 복사한다. 최대 64개 액션의 이름은 선형 탐색한다는 ponytail 한계와 측정 후 인덱스 도입 조건을 남겼다. 별도 성능 개선 수치를 주장하지 않는다.

데이터/실행: 선택 inputMap 필드가 없는 이전 manifest는 기존 기본 조작을 사용하고, 명시된 잘못된 버전·필드·세기/코드/방향/패드·중복·상한은 Expected로 거부한다. ProjectContext와 MyGame은 같은 LoadGameInputMap을 사용한다. ## 2026-10-03 · 방향 변경의 시간 비율·반전 발 피벗

요구와 범위: 가벼운 온라인 2D 픽셀 MMORPG 제작이라는 최종 목표에 따라 D08c를 공통 재생/미리보기/완료 전환(D08c1)과 재생 도중 연속 온라인 검증(D08c2)으로 나눴다. 공식 2D 애니메이션의 변경·프레임 진행률·pause/stop 구현을 먼저 확인했으며 상세 링크/차이는 로컬 build/2d-foundation/d08c-benchmark.md에 기록했다. 외부 구현을 복사하지 않았고 기존 라이선스 고지를 유지했다. 제품 설명은 실제 지원 계약으로 쓴다. 새로운 3D 기능·픽셀 제작기·패키지·에이전트는 추가하지 않았다.

원인과 재현: 방향이 바뀌어도 숫자 step/timeInStep을 그대로 쓰면 프레임 수/시간이 다른 클립의 진행 위치가 달라진다. 완료 커서도 더 짧은 클립에서 modulo되어 첫 프레임을 표시할 수 있다. 먼저 기존 AnimationTests에 저장 방향·표시/틱 경계 회귀를 추가했다. 수정 전 Debug CTest는 586/587, 37.40초이며 진행 위치/표시/이벤트 관련 기대 5개가 실패했다(d08c-before-tests.log). 방향별 파일 로드나 단일 프레임 색 검사만으로 발견하지 못했던 결함이다.

공통 경계: 기존 ClipPlayback의 StepDuration/ClipStepPeriod/StepToFrameSlot을 재사용한 RemapClipCursor는 논리 주기의 경과 초/전체 초 비율로 대상 위치를 계산한다. 정방향·역방향·왕복의 실제 순서와 서로 다른 시간 합계를 사용한다. 합계는 double, 저장 커서는 기존 float이며 경계 바로 전 값이 float 반올림으로 다음 경계가 되면 nextafter로 보존한다. 빈/0/비유한 메모리 클립은 안전한 초기 커서로 반환하며 저장 파일의 엄격 검증은 그대로 유지한다. 완료된 모션은 방향 변경만으로 다시 시작하지 않고 대상의 논리 마지막 스텝에서 완료 상태를 유지한다. 이미 존재하는 메모리 상태 머신의 keepPhase도 같은 보정을 사용하되 완료 뒤 새 상태/keepPhase=false는 처음부터 진입한다. 에디터의 행동 상태 작성 기능을 완료한 것은 아니다.

표시와 고정 틱: SpriteAnimator의 비직렬화 playbackFacing은 고정 틱 커서가 속한 방향만 기억한다. 이전 클립 포인터를 추가 보관하지 않고 같은 저장 에셋/상태에서 방향을 다시 해석해 에셋/문서 값 복사에 따른 수명 위험을 늘리지 않는다. SampleAnimator는 임시 보정 커서로 프레임/피벗/반전을 보여주며 커서·방향 이력·시작 이벤트를 소비하지 않는다. UpdateAnimator만 보정 위치와 방향을 커밋하고 AdvanceClip으로 진행한다. 보정 자체는 무음 seek이며 이미 지나간/현재 마커를 재발행하지 않는다. 이후 실제 경계 통과만 기존 고정 틱 이벤트로 전달한다. 새 에셋/상태 진입은 기존 첫 마커 규칙을 유지한다. 모든 요청/바인딩의 started=false 리셋 경로와 기존 후속 모션 호출자를 확인했다.

실제 소비자: 로컬 ObjectSystem 이동→UpdateCharacterAnimation2D→MyEditor/MyGame BindAnimations→RunAnimationSystem과 인증 MyGame TickOnline2D의 예측/원격 facing이 같은 재생 계산을 사용한다. 애니메이션 패널의 방향 선택도 이 보정을 사용하며 m_playing을 유지한다. 타임라인 변경/Undo/시트 교체는 기존 커서 초기화를 유지한다. 별도 시계/직렬화 버전/네트워크 패킷을 추가하지 않았다. 온라인 표현 시간은 클라이언트별이며 서버가 복제하는 모션 시계나 권위 피해 상태가 아니다.

발점 원인과 수정: UV만 뒤집으면 비대칭 원본 발점이 월드 앵커에서 움직였다. SpriteGeometry에서 flipX/flipY의 피벗을 너비−pivotX/높이−pivotY로 계산한다.
