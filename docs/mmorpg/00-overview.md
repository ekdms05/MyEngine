# 픽셀 2.5D MMORPG 확장 안내

MyEngine의 현재 앱·모듈을 바탕으로 온라인 RPG를 확장할 때 확인할 요구사항과 책임 경계를 안내한다. 현재 제품의 사용법은 [엔진 개요](../00-overview.md), 실제 앱 연결은 [구조와 기능](../13-architecture-and-features.md), 작업 순서는 [개발 우선순위](../14-development-priorities.md)를 따른다.

## 현재 사용할 수 있는 기반

| 영역 | 현재 동작 | 확장 전에 확인할 한계 |
|---|---|---|
| 클라이언트 | MyGame의 타이틀·설정·로컬 플레이, 프로젝트 로드, 온라인 이동·예측·재조정·원격 보간 | 전투·사회·사냥 콘텐츠가 앱에 연결되지 않음 |
| 에디터 | MyEditor의 패널·Inspector·뷰포트·타일/애니메이션 편집·분리된 플레이 월드 | 실제 프로젝트/씬 열기 미연결 |
| 렌더 | DX11의 2D·3D 공통 깊이, 픽셀 타깃·업스케일 | GPU 타임스탬프·청크 스트리밍·후처리 미연결, 대규모 성능 실측 필요 |
| 서버 | Windows 루프백 UDP, 입력·권위 이동·스냅샷, 64명 상한 | 외부 서비스용 세션 인증·신뢰 이벤트·AoI·다중 존 미완성 |
| 계정·저장 | CNG PBKDF2, JSON 상태 파일·검증·원장·세대 백업 | DB/WAL/PITR·분산 트랜잭션·정전 무손실 보장은 없음 |
| 제작 도구 | GUID/VFS/AssetManager, 에셋 임포터, Lua·runtime 라이브러리, paktool, MCP 8개 도구 | 라이브러리 존재와 게임 앱 연결을 구분해야 함 |

서버 틱·입력·스냅샷 주기는 현재 설정과 프로토콜 계약을 따른다. 클라이언트와 서버의 동일 이동·충돌 계약은 아직 완결되지 않았으므로, 같은 코드 기반이라는 이유만으로 결정론을 보장하지 않는다.

현재 코드의 책임은 `engine/` 공유 기반, `game/` 게임 규칙, `apps/` 실행 조합으로 나뉜다. 도메인 문서가 다른 번호나 미작성 자료를 참조하면 위의 실제 파일을 먼저 확인한다. 구현 상태를 판단할 때는 소스의 최종 소비자까지 추적한다.

## 공통 계약

- 좌표는 왼손 좌표계·+Y up, 기본 PPU 48, 픽셀 타깃 960×540이다. 깊이 밴드·Y 정렬·alpha cutout은 [렌더링 계약](../02-rendering.md)을 공유한다.
- 시뮬레이션은 고정 틱에서 처리한다. 렌더·UI는 표현 단계이며 서버 판정을 대신하지 않는다.
- `ecs::Entity`는 프로세스 내부 식별자다. 네트워크·저장 ID와 에셋 GUID의 수명·용도를 혼동하지 않는다.
- 패킷 길이·버전·세션·순서·범위와 파일 파싱 결과를 신뢰 경계에서 검증한다. 인증·경제·저장 실패를 성공처럼 진행하지 않는다.
- 콘텐츠와 에셋은 기존 GUID/VFS/AssetManager·직렬화 경로를 재사용한다. 별도 ID 체계나 생성 서비스를 먼저 추가하지 않는다.

## 확장 시 결정할 사항

| 항목 | 결정 근거·완료 조건 |
|---|---|
| 외부 네트워크·세션 | 인증된 전송·재접속·timeout·틱 협상·신뢰 이벤트가 실제 앱에서 동작해야 함 |
| 이동·충돌 | 지연·손실·장애물·높이 경계에서 서버와 클라이언트가 동일 계약으로 재조정되어야 함 |
| 서버 프로세스 구성 | 현재 단일 Windows 서버의 한계를 부하로 확인한 뒤 존 분리·플랫폼 확장 여부 결정 |
| 저장 확장 | 실제 쓰기량·복구 요구가 JSON 저장 한계를 넘을 때 DB·저널·PITR 도입 근거 기록 |
| 복제 권한 | server-only/client-visible 필드와 이벤트 순서를 게임 판정·저장 계약과 함께 정의 |
| 존·샤드 이전 | 메모리 권위와 저장 원장 사이의 단절·재시도에서도 아이템/화폐 중복·유실이 없어야 함 |
| 대량 렌더·복제 | 동일 Release 장면에서 CPU/GPU·배치·할당·네트워크 바이트를 측정하고 목표 수용량 결정 |
| 제작·운영 도구 | 실제 반복 작업·콘텐츠 양으로 필요성을 확인하고 검수·출처·버전/복구 조건 정의 |

수백~수천 명 동접·대규모 광장의 프레임 유지·24시간 분산 운영은 확장 목표이며 실측 결과가 아니다. 현재 64명 상한과 루프백 운용을 외부 서비스 검증으로 확대 해석하지 않는다.

## 확인할 위험과 개선 목록

이동/충돌 계약 차이, 인증 없는 세션, 틱 협상 부재, 경제 상태의 권위·저장 경계, 에디터 파일 열기 미연결이 현재 우선 확인할 항목이다. 상세 근거와 완료 조건은 [개발 우선순위](../14-development-priorities.md)에 모은다.

소셜 관계·온보딩·튜토리얼, 다중 존·분산 서비스, 서명 패치·런처·재해 복구는 추가 설계가 필요하다. 기존 모듈을 연결하고 실제 검증한 뒤 필요가 입증된 기능부터 확장한다. 외부 모델명·라이브러리·서버 구성을 고정된 미래 전제로 삼지 않는다.
